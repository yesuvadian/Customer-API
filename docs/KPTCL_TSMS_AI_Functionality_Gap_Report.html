The 9 gaps that matter most

Curated across all 18 modules — the ones that are named, spec'd deliverables and are not just thin, but absent. Six items dropped this session after review confirmed they no longer belong here: two were fixed or found to already exist outright, two were declared explicitly out of scope, one restated a point already covered elsewhere, and the rest of one item's substance (SLA tracking, disposition mapping, the monthly report) had been resolved.

01
GovernanceNo tamper-evident audit log. Only scoped, purpose-specific logs exist (workflow transitions, billing) — none capture old value / new value / IP address on a generic entity change, and there's no 7-year retention logic anywhere in the codebase.
02
Partially closed this sessionDesign Problem Register is now a visible flag + a live alert — still not a trackable register. equipment_service.py's is_design_problem_candidate computes the cohort-level flag; it's now a red "DESIGN PROBLEM" pill on the Failure Reliability panel (previously fetched into a Flutter variable and never rendered — confirmed dead via flutter analyze's own unused-variable warning), and a new daily job (main.py's _check_design_problem_alerts) calls the previously-dormant notify_design_problem_alert() once per newly-flagged cohort, routed to CEE_TRANSMISSION_ZONE/EE_TLSS (real KPTCL roles, not the template's own generic hardcoded names). Still true, and still the real remaining gap: there's no persistent case entity — nothing an AEE/EE can open, annotate, or mark resolved; it's a live computed signal, not an ownable record.
03
Corrected — more precise, more severeThe CAR mechanism exists; its escalation notification is dead for the real org. There's a genuine 5-stage workflow (OBSERVATION_REPORTING → ASSIGNMENT → COMPLIANCE_SUBMISSION → COMPLIANCE_REVIEW → CLOSURE), a real per-observation due date (target_compliance_date), and a working overdue-check job with a notification event and email template. But _get_escalation_users() (annual_audit_service.py:310) hardcodes recipient roles as "Reviewing Officer" / "Supervisory Officer" / "Senior Management Approver" — zero of KPTCL's 22 real role names match any of these (verified live against the org). The escalation call is guarded by if escalation_users:, so for KPTCL specifically, this notification never fires at all — not misrouted, just silent. What's genuinely missing: it's not a separate CAR entity with its own number (corrective action is a field/stage on the same observation), and due-date tracking doesn't distinguish Critical severity from Major/Minor/Advisory.
04
AI Analytics 12.1 — one input cheaper to add than thoughtEquipment Health Score is one factor, not five. Computed as the mean of the latest test classification only — trend direction, age vs. service life, maintenance compliance, and failure history are never referenced in the formula. The age-vs-service-life input specifically is no longer "would need new computation logic": ai_graph.py's _life_bucket()/_life_left() already derive real age-band buckets from commissioned_date + equipment type (built for that page's own "Fleet Life Left" section) — wiring that existing helper into the score formula as a fifth factor is reuse, not new development. Trend, maintenance compliance, and failure history still have no equivalent existing computation to reuse.
05
Corrected — config, not codeThe 10 repair stages are currently the wrong 10 — but relabeling them is a JSON edit. Today's stages (Failure Reporting → Committee Review → Vendor Assignment → Lifting → …, REPAIR_WORKFLOW_STAGES.json) are administrative/logistics, not the spec's workshop-repair sequence (oil draining, core & coil inspection, rewinding, assembly, pre-oil testing, oil filling). But the file is a flat [{name, sequence}] array with zero hardcoded stage-code references anywhere in services/ — unlike Annual Audit, which does hardcode its stage codes in Python. Redefining these 10 to match the spec is a data change through the existing Workflow Configuration admin UI, not new development.
06
RBACNo Read-Only Viewer role, no user-approval gate. 8 of the 10 spec'd roles exist by close/exact name — Read-Only Viewer is the one genuinely missing. New user accounts also activate immediately; there's no admin-approval step before login is possible.
07
CorrectionScheduled reports generate but never actually get emailed — the missing piece is narrower than first reported. run_scheduled_reports() (reporting_service.py:1080) really does run daily/weekly/monthly via APScheduler, and on-demand "email me this report" genuinely works over SMTP (routers/reporting.py:337-362). A full "report ready" notification-event catalogue was even seeded per report with sensible default roles (seed.py:10072-10152 — overdue_report_ready, pm_report_ready, etc.) — but nothing in run_scheduled_reports() ever calls NotificationService.fire() to trigger them. The plumbing exists on both ends; the one call connecting them was never written.
08
IntegrationSMTP/SMS credentials are .env-only. The spec asks for admin-console-configurable integration settings — changing a mail server or SMS provider today means editing an environment file and restarting the service.
09
AI Analytics 12.3 — one dimension closed this sessionCohort benchmarking is now missing one of its five dimensions, not three. Within-cohort outlier detection was built this session: a real Z-score comparison of each unit against its cohort peers, org-configurable threshold, with an OUTLIER badge on both the Overall Dashboard and Equipment Registry drill-downs (verified live, e.g. WS Industries CT cohort at Z=4.48). "No ALERT/CRITICAL-rate ranking" was also previously overstated — by_make_model_health (routers/analytics.py:524-573) gives real Critical/High/Medium/Low equipment counts per cohort, a genuine ALERT/CRITICAL-equivalent breakdown, just not sliced by voltage tier or presented as a sorted ranking. What's still genuinely missing: cohorts group by make/model/equipment-class only — equipment_service.py's cohort key is a hardcoded (equipment_type, manufacturer, model_number) tuple, not config-driven, so there's no voltage-class or age-band grouping dimension. Still structural (the grouping key reshapes the data, unlike the other two which were independent checks layered on top of the existing cohort computation) — but age-band specifically is now confirmed cheaper than "structural" implies: ai_graph.py's _life_bucket() already computes the exact age-band buckets this would need (see priority gap #4), so extending the cohort key to include it is reusing an existing helper, not deriving a new age dimension from scratch. Voltage-class has no equivalent existing helper and would still need one.
